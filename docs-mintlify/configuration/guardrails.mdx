---
title: "Guardrails"
description: "Match-and-effect policies evaluated on every request — deny, flag, or require approval."
---

A guardrail policy (`/api/policies`) matches requests on criteria you define and applies an
effect. Unlike budgets, guardrails aren't about spend — they're about *which* requests are
allowed to happen at all.

```jsonc
// POST /api/policies   (session or admin-key auth)
{
  "name": "block-gpt-4-for-interns",
  "description": "Interns can't use the expensive tier",
  "effect": "require_approval",
  "reason": "gpt-4.1 requires manager approval for the intern team",
  "match": {
    "team_ids": ["<intern-team-uuid>"],
    "models": ["gpt-4.1"]
  },
  "enforcement": "enforce",
  "enabled": true
}
```

## Fields

| Field | Type | Notes |
| --- | --- | --- |
| `name` | string, required | |
| `description` | string | |
| `effect` | `deny` \| `require_approval` \| `flag`, required | What happens when the policy matches. |
| `reason` | string, required | Shown to the caller (deny/approval) and logged in the decision log. |
| `match` | object | `virtual_key_ids`, `team_ids`, `models`, `metadata` — any combination; a request matches if it satisfies the criteria you set. |
| `conditionCel` | string \| null | An additional [CEL](https://github.com/google/cel-spec) expression for conditions `match` can't express. Authoring-time errors (`cel_parse_error`, `cel_type_error`, and related codes) are returned on create/update, not discovered at request time. |
| `enforcement` | `shadow` \| `enforce`, default `enforce` | `shadow` evaluates and logs the decision without actually applying the effect — the way to test a new policy against live traffic before it can block anything. |
| `enabled` | boolean, default `true` | |
| `effectConfig` | object | Effect-specific configuration (for example, which approval policy a `require_approval` effect opens against). |

## The three effects

- **`deny`** — the request is blocked with `403` before dispatch. No provider call, no
  charge.
- **`require_approval`** — the request is blocked with `403` and an approval request is
  opened against the effect's approval policy (see
  [Approvals & automation](/configuration/approvals-and-automation)). The caller has to
  retry once it's approved; there's no automatic hold-and-resume.
- **`flag`** — the request proceeds normally. The match is recorded in the decision log for
  visibility, with no effect on the response.

## Testing before you enforce

Two ways to see what a policy *would* do before it can block real traffic:

- Set `enforcement: "shadow"` on the policy itself — it evaluates on every real request and
  logs the decision, but never denies or gates one.
- `POST /api/policies/{id}/shadow-impact` — run a policy against recent traffic on demand to
  see its hit rate before flipping it to `enforce`.

`POST /api/policies/lint` validates a policy's `match`/`conditionCel` without creating it —
useful for catching a malformed CEL expression before it ever reaches the database.
